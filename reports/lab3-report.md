## 1. Опис реалізованого функціоналу

У межах лабораторної роботи виконано розгортання вебсервісу Task Manager API на платформі Railway та перевірено його основну працездатність. Застосунок реалізовано з використанням Node.js, Express.js, PostgreSQL, Prisma ORM та Socket.IO.

### 1.1. Автентифікація та авторизація

Реалізовано реєстрацію й авторизацію користувачів із використанням JWT. Передбачено оновлення та відкликання refresh-токенів, зміну пароля, отримання даних поточного користувача й захист маршрутів від неавторизованого доступу. Для зберігання паролів використовується хешування Argon2id.

### 1.2. Керування даними

Реалізовано функціонал створення, перегляду, редагування та видалення проєктів і завдань. Також передбачено роботу з користувачами, коментарями та файлами. Для завдань реалізовано пошук, фільтрацію й пагінацію. Під час завантаження файлів сервер перевіряє їхній тип і розмір.

### 1.3. Система сповіщень

Реалізовано отримання сповіщень користувачів, позначення їх прочитаними та видалення. Сповіщення зберігаються в PostgreSQL, що дає змогу отримувати їх через REST API.

### 1.4. Взаємодія в реальному часі

Для обміну подіями між сервером і клієнтами використовується Socket.IO. Реалізовано перевірку JWT під час підключення, відстеження онлайн-статусу користувачів і механізм приєднання до кімнат проєктів із перевіркою прав доступу.

Передбачено події, пов’язані зі створенням, оновленням і видаленням проєктів, завдань і коментарів, а також передавання персональних сповіщень.

### 1.5. Документація API

Для документування серверних маршрутів використовується Swagger UI. Документація містить опис API та дає змогу переглядати доступні маршрути й параметри запитів.

### 1.6. Розгортання вебсервісу

Застосунок розгорнуто на платформі Railway. Налаштовано змінні середовища для підключення до PostgreSQL і роботи JWT-автентифікації. Для застосування міграцій бази даних у production-середовищі використовується Prisma.

## 2. Перевірка працездатності

Під час перевірки розгорнутого застосунку отримано такі результати:

- Запит `GET /api/health` повертає HTTP 200, що підтверджує доступність сервера.
- Запит `GET /api-docs/` повертає HTTP 200, документація API доступна.
- Запити до захищених маршрутів без токена повертають HTTP 401.
- Запити до захищених маршрутів із недійсним токеном також повертають HTTP 401.

Результати підтверджують доступність розгорнутого вебсервісу та роботу базової перевірки автентифікації. Повне тестування всіх CRUD-операцій і взаємодії між кількома WebSocket-клієнтами в межах цієї перевірки не проводилося.
