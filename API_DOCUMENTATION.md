# Task Manager API Documentation

## 1. Загальна інформація

**Назва проєкту:** Task Manager API

**Опис:** REST API для керування користувачами, проєктами, завданнями, коментарями та сповіщеннями.

**Локальна адреса:**
```text
http://localhost:3000
```

**Адреса розгорнутого застосунку Railway:**

https://task-manager-api-production-154a.up.railway.app

**Документація Swagger:**

https://task-manager-api-production-154a.up.railway.app/api-docs/

**Використані технології:**
- Node.js
- Express.js
- PostgreSQL
- Prisma ORM
- Zod для валідації даних
- JWT для авторизації
- Socket.IO для взаємодії в реальному часі
- Railway для розгортання

Для передавання даних через REST API використовується формат JSON.

## 4. Користувачі (Users)

### Створення користувача

**POST** `/api/users`

Тіло запиту:

```json
{
  "name": "Test User",
  "email": "test@example.com"
}
```

Приклад відповіді:

```json
{
  "id": 1,
  "name": "Test User",
  "email": "test@example.com",
  "createdAt": "2026-10-19T12:50:59.263Z"
}
```

Це приклад структури відповіді. Фактичні значення залежать від даних у базі.

### Отримання списку користувачів

**GET** `/api/users`

Повертає список зареєстрованих користувачів.

### Отримання користувача за ID

**GET** `/api/users/:id`

Приклад: `/api/users/1`.

### Оновлення користувача

**PUT** `/api/users/:id`

Тіло запиту:

```json
{
  "name": "Updated User"
}
```

### Видалення користувача

**DELETE** `/api/users/:id`

Видаляє користувача із зазначеним ідентифікатором, якщо це дозволяють пов'язані записи бази даних.

## 5. Проєкти (Projects)

### Створення проєкту

**POST** `/api/projects`

Тіло запиту:

```json
{
  "name": "Test Project",
  "description": "Test project for API",
  "ownerId": 1
}
```

Поле `ownerId` містить ідентифікатор користувача — власника проєкту.

### Отримання списку проєктів

**GET** `/api/projects`

Повертає список проєктів із пов'язаною інформацією про власника та завдання.

### Отримання проєкту за ID

**GET** `/api/projects/:id`

Приклад: `/api/projects/1`.

### Оновлення проєкту

**PUT** `/api/projects/:id`

Тіло запиту:

```json
{
  "name": "Updated Project",
  "description": "Updated project description"
}
```

### Видалення проєкту

**DELETE** `/api/projects/:id`

Видаляє проєкт за ідентифікатором, якщо це дозволяють пов'язані записи.

## 6. Завдання (Tasks)

### Створення завдання

**POST** `/api/tasks`

Тіло запиту:

```json
{
  "title": "Test Task",
  "description": "Test task for API",
  "projectId": 1,
  "assigneeId": 1
}
```

`projectId` визначає проєкт, до якого належить завдання. `assigneeId` визначає користувача, якому призначено завдання.

### Отримання списку завдань

**GET** `/api/tasks`

Повертає список завдань із пов'язаними проєктами, виконавцями та коментарями.

### Отримання завдання за ID

**GET** `/api/tasks/:id`

Приклад: `/api/tasks/1`.

### Оновлення завдання

**PUT** `/api/tasks/:id`

Тіло запиту:

```json
{
  "status": "IN_PROGRESS"
}
```

Можливі статуси:
- `TODO` — завдання ще не розпочато;
- `IN_PROGRESS` — завдання виконується;
- `DONE` — завдання завершено.

Можливі пріоритети: `LOW`, `MEDIUM`, `HIGH`.

### Видалення завдання

**DELETE** `/api/tasks/:id`

Видаляє завдання за ідентифікатором, якщо це дозволяють пов'язані записи.

## 9. Формат запитів та авторизація

Для запитів, які передають дані, використовується заголовок:

```text
Content-Type: application/json
```

Для захищених маршрутів потрібно передавати JWT-токен:

```text
Authorization: Bearer <JWT_TOKEN>
```

Ідентифікатор `:id` у URL потрібно замінювати на фактичний ID запису, наприклад `/api/users/1`.

## 10. Обробка помилок

Залежно від маршруту API може повертати такі HTTP-статуси:

- **200 OK** — запит виконано успішно;
- **201 Created** — запис створено;
- **400 Bad Request** — некоректні дані запиту;
- **401 Unauthorized** — потрібна автентифікація або токен недійсний;
- **403 Forbidden** — недостатньо прав для виконання дії;
- **404 Not Found** — запис або маршрут не знайдено;
- **500 Internal Server Error** — внутрішня помилка сервера.

Приклад помилки:

```json
{
  "error": "Маршрут не знайдено"
}
```

Фактичний формат повідомлень залежить від маршруту та middleware обробки помилок.

## 11. WebSocket та Socket.IO

Для взаємодії в реальному часі використовується Socket.IO. Підключення виконується до адреси сервера з передаванням JWT-токена через параметр `auth`.

### 11.1. Підключення

У клієнтському застосунку потрібно встановити пакет `socket.io-client`.

Приклад підключення до розгорнутого сервера:

```javascript
import { io } from "socket.io-client";

const socket = io(
  "https://task-manager-api-production-154a.up.railway.app",
  {
    auth: {
      token: JWT_TOKEN
    }
  }
);

socket.on("connected", (data) => {
  console.log("Підключено:", data);
});

socket.on("connect_error", (error) => {
  console.error("Помилка підключення:", error.message);
});
```

Для локального запуску адресу потрібно замінити на `http://localhost:3000`.

### 11.2. Авторизація WebSocket

Під час встановлення з'єднання сервер перевіряє JWT-токен, отриманий через `socket.handshake.auth.token`.

Якщо токен відсутній, недійсний або прострочений, підключення відхиляється. Ідентифікатор користувача та його роль визначаються за перевіреним токеном.

### 11.3. Події Socket.IO

| Подія | Напрямок | Призначення |
|---|---|---|
| `connected` | Сервер → клієнт | Підтверджує підключення та передає ID користувача |
| `presence:list` | Сервер → клієнт | Передає список ID користувачів онлайн |
| `presence:get` | Клієнт → сервер | Запитує актуальний список користувачів онлайн |
| `presence:update` | Сервер → клієнти | Повідомляє про появу користувача онлайн або його вихід |
| `room:join` | Клієнт → сервер | Запитує приєднання до кімнати проєкту |
| `room:joined` | Сервер → клієнт | Підтверджує приєднання до кімнати |
| `room:leave` | Клієнт → сервер | Запитує вихід із кімнати проєкту |
| `room:left` | Сервер → клієнт | Підтверджує вихід із кімнати |
| `socket:error` | Сервер → клієнт | Повідомляє про помилку або відсутність доступу |

### 11.4. Присутність користувачів

Після підключення сервер додає користувача до персональної кімнати формату `user:{userId}` і відстежує його активні з'єднання.

Подія `presence:list` містить список ідентифікаторів користувачів онлайн. Для повторного отримання списку клієнт надсилає подію `presence:get`.

Подія `presence:update` повідомляє про зміну статусу користувача. Статус може мати значення `online` або `offline`.

Приклад даних події:

```json
{
  "userId": "16",
  "status": "online",
  "timestamp": "2026-10-20T12:00:00.000Z"
}
```

Це приклад структури повідомлення; фактичні значення формуються сервером.

### 11.5. Кімнати проєктів

Для групування з'єднань за проєктами використовуються кімнати формату `project:{projectId}`.

Приклад приєднання до кімнати:

```javascript
socket.emit("room:join", 1);

socket.on("room:joined", (data) => {
  console.log("Приєднано до проєкту:", data.projectId);
});

socket.on("socket:error", (error) => {
  console.error(error.message);
});
```

Перед приєднанням сервер перевіряє, чи є користувач власником проєкту або виконавцем завдання в цьому проєкті. Якщо доступу немає, сервер надсилає подію `socket:error`.

Приклад виходу з кімнати:

```javascript
socket.emit("room:leave", 1);

socket.on("room:left", (data) => {
  console.log("Вихід із проєкту:", data.projectId);
});
```

### 11.6. Відключення користувача

Після відключення клієнта сервер видаляє відповідне з'єднання зі списку активних з'єднань. Якщо в користувача більше немає активних з'єднань, сервер прибирає його зі списку онлайн і повідомляє інших клієнтів через `presence:update` зі статусом `offline`.

Список онлайн зберігається в пам'яті сервера, тому після перезапуску сервера формується заново.

https://task-manager-api-production-154a.up.railway.app/api-docs/

**Health endpoint:**

### 12.1. Змінні середовища

Для роботи застосунку необхідно налаштувати такі змінні:

- `DATABASE_URL` — рядок підключення до PostgreSQL;
- `JWT_SECRET` — секретний ключ для перевірки JWT;
- `PORT` — порт сервера, який може задавати платформа;
- `CLIENT_URL` — дозволене джерело клієнтського застосунку для CORS Socket.IO.

Секретні значення потрібно зберігати в налаштуваннях середовища Railway та локальному файлі `.env`. Файл `.env` із секретами не слід додавати до публічного репозиторію.

### 12.2. Локальний запуск

1. Встановити Node.js і підготувати доступ до PostgreSQL.
2. Клонувати репозиторій і перейти до каталогу проєкту.
3. Встановити залежності:

```bash
npm install
```

4. Створити файл `.env` і налаштувати необхідні змінні середовища.
5. Застосувати міграції для локальної бази даних:

```bash
npx prisma migrate dev
```

6. Запустити сервер:

```bash
npm run dev
```

7. Відкрити документацію за адресою `http://localhost:3000/api-docs/`.

### 12.3. Виробниче розгортання

Встановлення залежностей і генерація Prisma Client:

```bash
npm ci
npx prisma generate
```

Застосування наявних міграцій у виробничій базі:

```bash
npx prisma migrate deploy
```

Команда запуску сервера:

```bash
node src/server.js
```

## 13. Результати перевірки розгорнутого застосунку

Під час перевірки розгорнутого сервера отримано такі результати:

| Перевірка | HTTP-статус | Результат |
|---|---:|---|
| `GET /api/health` | 200 | Сервер доступний |
| `GET /api-docs/` | 200 | Swagger доступний |
| `GET /api/auth/me` без токена | 401 | Запит відхилено |
| `GET /api/projects` без токена | 401 | Запит відхилено |
| `GET /api/tasks` без токена | 401 | Запит відхилено |
| `GET /api/notifications` без токена | 401 | Запит відхилено |
| `GET /api/auth/me` з недійсним токеном | 401 | Недійсний токен відхилено |
| `GET /api/projects` з недійсним токеном | 401 | Недійсний токен відхилено |

Результати підтверджують доступність сервера та Swagger, а також відхилення запитів до зазначених захищених маршрутів без дійсного JWT-токена.

Ці перевірки не підтверджують повне тестування всіх CRUD-операцій, створення записів у базі даних або всіх WebSocket-подій.
